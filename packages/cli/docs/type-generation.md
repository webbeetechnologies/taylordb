# Type Generation

The CLI can introspect a live TaylorDB app and emit a fully-typed TypeScript file you can import directly into your query-builder setup.

## Command

```bash
taylordb generate-schema <appUrl> <output>
```

| Argument | Required | Description |
|----------|----------|-------------|
| `appUrl` | yes | Either the full TaylorDB app URL (e.g. `https://app.taylordb.ai/123`) **or** a bare UUID that identifies the database directly |
| `output` | yes | Path to the `.ts` file that will be created/overwritten (e.g. `src/taylorclient.types.ts`) |

You must be authenticated before running this command. Use `taylordb login` or `taylordb set-token <token>` first.

## What it accepts

### `appUrl` — two formats

**Full URL**
The numeric ID is extracted from the last URL path segment and resolved to an internal database UUID via the TaylorDB API.

```
https://app.taylordb.ai/workspaces/my-workspace/databases/42
                                                            ^^
                                                            parsed as the app ID
```

**Bare UUID**
If the value already matches `/^[0-9a-fA-F]{8}-…/`, it is used as-is without an extra lookup.

```
taylordb generate-schema 7f3e1c2a-0001-0002-0003-000000000000 ./types.ts
```

## What you get

A single `.ts` file is written to `<output>`. It contains:

### `TaylorDatabase` type

The root type you pass as the generic to `createQueryBuilder`. Every non-internal table in your app becomes a property on this object.

```ts
export type TaylorDatabase = {
  users: UsersTable;
  posts: PostsTable;
  // one entry per table
};
```

### One `*Table` type per table

Each table type maps every non-internal field to one of the column types exported from `@taylordb/shared`. The mapping from TaylorDB field type to TypeScript column type is:

| TaylorDB field type | Generated column type |
|---------------------|-----------------------|
| `singleLineText`, `text`, `longText`, `url`, `email`, `phoneNumber`, `json` | `TextColumnType<boolean>` |
| `number`, `currency`, `percent`, `duration`, `serial`, `decimalSerial`, `position` | `NumberColumnType<boolean>` |
| `autoNumber` | `AutoGeneratedNumberColumnType` |
| `checkbox` | `CheckboxColumnType<boolean>` |
| `date` | `DateColumnType<boolean>` |
| `createdAt`, `updatedAt`, `modifiedAt` | `AutoGeneratedDateColumnType` |
| `select` (single) | `SingleSelectColumnType<typeof XxxOptions, boolean>` |
| `select` (multi) | `MultiSelectColumnType<typeof XxxOptions, boolean>` |
| `link` | `LinkColumnType<'linkedTableName', boolean>` |
| `collaborators`, `modifiedBy` | `LinkColumnType<'collaborators', boolean>` |
| `attachment` | `AttachmentColumnType<boolean>` |
| `search` | `SearchColumnType` |

The `boolean` generic on each column type reflects whether the field is marked **required** in your TaylorDB schema (`true`) or optional (`false`). This propagates into insert/update type-checking in the query builder.

Fields with an unrecognised type but a known `returnType` (`string`, `number`, `boolean`, `date`) fall back to the matching column type.

### Select-field option constants

For every `select` field a `const` array is exported containing the allowed option values. This is what feeds the `typeof XxxOptions` generic above.

```ts
export const UsersRoleOptions = ['admin', 'editor', 'viewer'] as const;
```

Naming pattern: `{PascalCaseTableName}{PascalCaseFieldName}Options`.

### Plugin types (when plugins exist)

If the app has any plugins configured, additional types are generated:

- `PluginActionType<I, O>` — generic wrapper `{ input: I; result: O }`.
- Per-action input/output types compiled from the plugin's JSON Schema.
- A `_plugin` property on `TaylorDatabase` mapping each plugin and action to its `PluginActionType`.

### Default system fields

Every table automatically includes these system-level fields (merged before your custom fields):

| Field | Type |
|-------|------|
| `id` | `AutoGeneratedNumberColumnType` |
| `createdAt` | `AutoGeneratedDateColumnType` |
| `updatedAt` | `AutoGeneratedDateColumnType` |

## Output example

```ts
import {
  AttachmentColumnType,
  AutoGeneratedDateColumnType,
  AutoGeneratedNumberColumnType,
  DateColumnType,
  LinkColumnType,
  MultiSelectColumnType,
  NumberColumnType,
  SingleSelectColumnType,
  TextColumnType,
} from '@taylordb/shared';

export const PostsStatusOptions = ['draft', 'published', 'archived'] as const;

export type UsersTable = {
  id: AutoGeneratedNumberColumnType;
  createdAt: AutoGeneratedDateColumnType;
  updatedAt: AutoGeneratedDateColumnType;
  name: TextColumnType<true>;
  email: TextColumnType<true>;
  age: NumberColumnType<false>;
  posts: LinkColumnType<'posts', false>;
};

export type PostsTable = {
  id: AutoGeneratedNumberColumnType;
  createdAt: AutoGeneratedDateColumnType;
  updatedAt: AutoGeneratedDateColumnType;
  title: TextColumnType<true>;
  status: SingleSelectColumnType<typeof PostsStatusOptions, false>;
  author: LinkColumnType<'users', false>;
};

export type TaylorDatabase = {
  users: UsersTable;
  posts: PostsTable;
};
```

## Formatting

The generated file is automatically formatted using the nearest **Prettier** or **ESLint** config found by walking up from the output path. If neither is found the raw output is written as-is.

## Other CLI commands

| Command | Description |
|---------|-------------|
| `taylordb login` | Interactive email/password login, stores the token locally |
| `taylordb logout` | Invalidates the current session and clears the stored token |
| `taylordb me` | Prints the name and email of the currently authenticated user |
| `taylordb set-token <token>` | Stores a token directly without going through the login flow |
